# There's a Dilbert for that!

Personal, offline search over the Dilbert archive. Describe an absurd workplace
situation or half-remembered strip and get the matching strips. Unofficial fan
project.

## Requirements

- Free-text search by situation or meaning as well as exact words.
- Each result shows `YYYY-MM-DD`, the title, and a 0-10 match score in 0.1 steps.
- Each result shows the strip's location under the archive folder with a copy button, and the strip itself when Show strips is on.
- Strip images load only from the user's own archive. Never bundle them in the app, the zip or the repo.
- An archive with different folders or filenames is supported by `index-archive.command`, a run-once script that ships with the app. It finds each file by the `YYYY-MM-DD` in its name and writes `archive-index.js` next to itself. The app uses that file if present, and the paths in `data.js` otherwise. `index-archive.bat` and `index-archive.ps1` do the same on Windows.
- Settings are saved per browser: Show strips (default on), Archive location (default `/Volumes/Public/Dilbert`, tested with Test location) and Strip size. Paths can be macOS, Linux or Windows style (`C:\Dilbert`, `\\NAS\Public\Dilbert`).
- Safari only lets a `file://` page load images from its own folder and below (tested: absolute paths, parent folders and symlinks are blocked). So for Safari the app files go inside the archive folder, next to the year folders. The app detects this at startup and uses its own folder as the archive. Chrome works from anywhere.
- Web interface opened directly from `index.html` (`file://`). No launcher, no server, nothing to install, no API key.
- Delivered as `DilbertSearch.zip`: unzip and open.

## Decisions

- Keep the page free of `fetch`, modules and workers. Browsers block them from `file://`, so everything loads through classic `<script>` tags, with the WASM and model embedded as base64.
- `src/embedder.js` is shared by the Node build and the browser, so vectors always match. `tools/check-embedder.mjs` confirmed it matches Transformers.js.
- The embedding model is `bge-small-en-v1.5`. It replaced `all-MiniLM-L6-v2`, which ranked strips far too low when a query's wording differed from theirs. Queries need `QUERY_PREFIX`, and `SEM_LOW` and `SEM_HIGH` in `src/search.js` are calibrated to this model.
- Titles are generated by Claude, because the strips have none. Scores are estimates, not probabilities.
- The repo holds no strip images. MIT covers the code only, and the README carries the fan-project notice.
- Keep `summary` free of quoted dialogue, and `transcript` a separate field, so public data could omit transcripts later.

## Layout

- `data/YYYY.jsonl`: extracted strips, all 12,384. Do not regenerate without asking: the run cost about $61.
- `data/vectors.json`, `vectors-summary.json`, `vectors-dialogue.json`: cached embeddings, one file per entry in `VIEWS` in `tools/build-app.mjs`, which only embeds strips missing from them. Delete a file after changing that view's text.
- `src/search.js`: ranking and score constants. `FEATURES` switches the extras: `characters` (boost for strips with a character the query names, with aliases like PHB) and `dates` (boost for a year, range or decade in the query, which is also removed before embedding). All are off until the eval shows they help; try them with `--with=all` on `tools/eval.mjs` or `tools/try-search.mjs`. They add about 0.3 s to building the index at load. `views` is on: each strip has three vectors (description, summary, dialogue) and the best match counts, after `VIEW_OFFSET` is taken off. Without the offsets the summary and dialogue views made ChatGPT's results worse. `src/app.js`, `src/index.html`: the page. `src/paths.js`: archive paths and `file://` links, checked by `tools/check-paths.mjs`. `src/index-archive.command`, `.ps1` and `.bat`: the archive index scripts. `src/README.txt`: archive setup instructions for people who only get the zip; keep it in step with `README.md`.
- `tools/try-search.mjs "query" ...`: runs queries from the command line against `build/app/data.js`.
- `tools/eval.mjs`: `npm run eval` runs the ranking checks below and the test queries in every `eval/test-queries*.json`, and prints top 1, top 5, shown and MRR, overall and per file. It exits non-zero if a check fails. `--all` lists every query.
- `eval/sample-strips-1.jsonl`, `-2.jsonl`: separate sets of 5 strips per year from `tools/sample-strips.mjs` (set 1 for ChatGPT, set 2 for Gemini), for writing test queries in a chat with the prompt in `eval/PROMPT.md`. Test queries are for measuring only, never for indexing.
- `tools/extract.mjs`: the Sonnet 5.5 Batch API extraction. It needs the archive and an API key, and neither is on the Mac by default.
- `tools/package-app.mjs`: `npm run package` writes `build/DilbertSearch.zip` from `build/app/`. Run it after `npm run build`.
- `models/` and `build/` are not tracked. Run `npm run fetch-model`, then `npm run build`.

## Status

Done: extraction, index, working app built from all 12,384 strips, meaning search confirmed from `file://` in Safari and Chrome with a prototype, packaging, and the unzipped copy tested from `file://` in Chrome (load about 2.6 s, search under 50 ms, Copy works) and by the owner in Safari.

Ranking checks that must keep passing, run with `npm run eval` (they are in `CHECKS` in `tools/eval.mjs`):

- `We just had an anonymous satisfaction survey and we're only 5 people in the team. It's easy figure who answered what`: `2010-09-01` first.
- `Dogbert is a cloud expert`: the March 2020 strips above `1992-12-13`.
- `told to do a colleague's job as well with no extra resources`: `2005-09-16` in the top five. This depends on `SYNONYM_GROUPS`.
- `We had two projects running simultaneously with the same purpose but with no communication between them`: `2011-04-27` in the results.
- `We had a manager requesting completely impossible metrics and we ended just suggesting random stuff`: `2013-08-31` in the results. This also depends on `SYNONYM_GROUPS`.
- `cloud bunny`: `1992-12-13` first. `quality approaches zero`: `2005-09-16` first.

Baseline with one vector per strip, MRR: ChatGPT 0.766, Gemini 0.507. With three: 0.781 and 0.533 (top 5: 87.6% to 87.8%, 61.3% to 64.6%). Offsets were picked looking at both query sets, so later tuning has no untouched set.

Changes in `src/search.js` need only a rebuild. Changes to a view's text mean deleting its vector file and re-embedding, about 7 to 15 minutes per file.

Tuning the constants was tried and dropped: 400 combinations of the keyword, meaning, synonym and offset settings gained at most 0.003 MRR, and did no better on queries held out from tuning. Search is weakest on heavily reworded queries, which would need something like a stronger embedding model.

Possible later: `characters` and `dates` stay in the code, switched off and untested. Turning them on would first need a small test query set with names and dates, which the current sets cannot trigger.
